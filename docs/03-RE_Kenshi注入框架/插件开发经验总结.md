# KenshiLib 插件开发经验总结

> 2026-09-16 整理。来源：KenshiTrainer 修改器开发过程中属性修改、物品生成、
> 武器关联等功能的实战经验。与《RE_Kenshi与KenshiLib开发指南》《关键API速查》互补。

## 一、先搞清楚的三个底层认知

### 1. GameData 是一切的载体

Kenshi 没有为每类定义生成 C++ 类，几乎所有静态定义（武器/护甲/制造商/模型…）都是
通用 `GameData`，数据存放在四个容器里：

| 容器 | 内容 | 访问 |
|---|---|---|
| `idata` / `fdata` / `sdata` | 命名标量（伤害系数、重量、倍率…） | 直接迭代或按键查 |
| `objectReferences` | **命名引用列表**：`map<string, vector<GameDataReference>>` | 定义间关联都在这里 |
| `GameDataReference.values`（TripleInt） | 每个引用附带 3 个 int | `value[0..2]` |

**关键推论：定义之间的关联图在运行时就挂在 `objectReferences` 上**。
证据：盔甲 dump 显示 `[part coverage]`×4 + `[material]`×1；武器 dump 显示引用为空
（与 wiki 文档一致——武器类型本身不引用模型）。

### 2. Item 是三分结构

`Item(baseData=物品类型, companyData=制造商, materialData=模型/材质, handle)`。
游戏自己生成武器走 `Character::generateWeapon(weapon, manufacturer)`，
选模型的通用机制是 `RootObjectFactory::chooseDataFromList(dataList, listName, itemType, useVal012)`。
修改器生成物品的等价路径 CheatMenu 已验证：`new Sword(gd, manufacturer, model, hand, level)`。

### 3. GameDataManager 运行时合并所有启用 mod

`getDataOfType(list, itemType)` 枚举的是合并后数据库——**只要从运行时枚举和解析，
mod 内容天然被覆盖**，不需要解析 .mod 文件。这是本方案对"mod 兼容性"的通用答案。

## 二、功能实现的标准方法论（四步走）

### 第 1 步：查 fcs_chs.def，拿到字段定义（最重要）

`fcs_chs.def`（FCS 汉化定义文件，1875 行）按 `[数据类型]` 分节列出每个字段的
**数据键名、引用类型、引用值（TripleInt）语义、中文说明**。这是把"游戏行为"
翻译为"数据结构"的权威字典。

已验证的关键条目（`[WEAPON_MANUFACTURER]` 节）：

```
weapon types:  WEAPON               (val0=几率)              ← 我能做哪些武器
weapon models: MATERIAL_SPECS_WEAPON (val0=武器等级[1-100], val1=几率)  ← 我用哪些模型、各多少级
price mod / blunt damage mod / cut damage mod / min cut damage / weight mod / faction owner
```

**武器等级不在模型上，而在制造商对模型的引用值上**——这是"模型↔等级关联"的数据根源。
（模型的 `idata` 里那个 "level" 键不可靠，别用。）

### 第 2 步：用 KenshiLib 头文件验证运行时结构

克隆 KenshiLib 仓库（`RE_Kenshi_mods` 分支，800+ 头文件）查类定义。
本地 `reference/KenshiLib_include/` 只是子集。
要确认的：构造函数参数序、成员偏移、相关机制函数（如 `chooseDataFromList`）。

### 第 3 步：写防御式解析 + 紧凑诊断日志

- **按引用元素类型分类，不猜字段名**。字段显示名随语言/数据变化，类型枚举
  （WEAPON / MATERIAL_SPECS_WEAPON / …）稳定。一个列表里有 WEAPON 引用就是
  weapons 列表，有 MATERIAL_SPECS_WEAPON 引用就是 models 列表。
- **引用值解析要容错**：TripleInt 哪个槽位是语义值文档记号混用，做
  "在合理范围内（如 1-100）找第一个像的值"的回退。
- **诊断日志一行一个实体、短行**：`mfr '刃行者' weapons=18(...) models=3(刃之一[lv70/ch10];...)`
  。教训：几百 KB 的大段 dump 通过 DebugLog 输出可能整段丢失（原因未查明），
  紧凑单行必定落盘。
- 解析失败必须**逐层回退到旧行为**（过滤无果→全列表），保证功能退化不劣化。

### 第 4 步：用户实测闭环

实测是最便宜的真值来源。一个具体例子：刃之三游戏内=80 级，与 val0 解析值一致，
一步验证了"槽位+语义"两个假设。**在功能里埋好可核对的输出**（生成回读
`manufacturer=… material=… lv=…`、每个制造商一行摘要），让用户的一次操作
同时完成验收和诊断。

## 三、武器生成功能的完整关联链（案例复盘）

```
选中武器 W
  └─ 制造商列表 = weapons 列表含 W 的制造商
     └─ 特例：有模型但 weapons 列表为空的制造商 = 通用制造商（十字/铭物），
        对全部武器可见——否则铭物从所有武器里消失（它只被独特 NPC 直接持有，
        原版数据里没声明任何武器类型）
        └─ 模型列表 = 所选制造商的 models 列表（未选=匹配制造商的并集）
           └─ 等级 = 模型引用 val0（1-100），选模型即预填，选品质项同时选中模型
```

三条经验：
1. **回退要分层**：无声明→全列表；无等级→猜键→静态阶梯。实测前每层的兜底都已就位。
2. **UI 条目从运行时数据动态生成**，名称与游戏天然一致，mod 内容自动正确。
   写死的名称表只作解析失败的兜底。
3. **游戏词汇分两套，别混**：武器是 15 级阶梯（生锈的垃圾→…→刃之三→铭物），
   护甲/弩是六档（模本5/赝品20/标准40/高60/专家80/杰作95，见
   《假肢数据的计算》grades 表）。早期把护甲词汇（普通/高级/杰作）用在武器上是错名。

## 四、工程约束备忘（本项目特有）

- **v100 工具链**：Release x64 唯一合法配置；源码里不能出现非 ASCII 字面量，
  UI 字符串全部走 `ChineseStrings.h` 的 UTF-8 hex 转义，**用 Python 脚本生成/修改，勿手改转义**。
- **SEH 规范（C2712）**：`__try` 块内禁止不可展开的局部对象（std::string/vector）。
  模式：Impl 函数放外面操作全局/静态缓冲，`SafeXxx` 只做 `__try{Impl()}__except{}`。
- **所有游戏 API 调用走 SafeXxx 包装**，绝不裸调。
- **编译即验证**：`powershell -ExecutionPolicy Bypass -File tools\build.ps1` 是唯一步骤，
  产物自动拷入 `mods/KenshiTrainer/`。无自动化测试，验证靠游戏内日志
  （`RE_Kenshi_log.txt` 的 `KenshiTrainer:` 行 + 生成回读）。

## 五、排错速查

| 症状 | 首要怀疑 |
|---|---|
| 某类条目全缺失 | 该类型没进 `GetCategoryTypes` 的枚举；或搜索过滤词 |
| 关联列表全空（weapons=0 models=0） | 运行时引用不在 `objectReferences`（改查 handle list），先开诊断日志确认 |
| 生成的武器品质名与所选不符 | 等级覆盖值与模型 val0 不一致；或模型/制造商传参顺序错（Sword 构造是 manufacturer 在前） |
| 铭物类模型不显示 | 通用制造商（空 weapons 列表）被过滤逻辑排除 |
| 日志里 dump 缺失 | DebugLog 长行丢失，改短行 |
| 修改器一进游戏就崩 | SafeXxx 遗漏 / `__try` 里塞了 unwindable 对象（编译期 C2712 会拦） |
